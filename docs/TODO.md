## 2. Надёжность Core / IPC — P0-P1

- **R-01** `✓` **Лимит сообщения не защищает память:** входная строка читается с ограничением
  длины во время чтения; oversized-сообщение закрывает соединение до JSON-десериализации.
- **R-02** `✓` **Зависшая IPC-команда:** обработчик получает токен отмены на подключение и
  ограничен таймаутом 14 с (клиентский RPC ждёт до 15 с); Core связывает его с токеном
  завершения. При превышении лимита сервер пишет диагностическое сообщение, возвращает ошибку
  и закрывает зависшее соединение. Обработчику, который игнорирует отмену, платформа не может
  принудительно остановить выполнение.
- **R-03** `✓` IPC-записи каждого клиента проходят через ограниченную FIFO-очередь и один sender;
  fire-and-forget события при заполнении отбрасываются с логированием, а ожидаемые отправки
  backpressure-ят издателя. Integration test проверяет порядок серии событий; независимые
  параллельные издатели по-прежнему упорядочиваются в порядке принятия очередью.
- **R-04** `✓` **Жизненный цикл IPC-подключений:** при закрытии завершается read-loop и
  освобождаются reader/writer/CTS; таймаут очистки явно логируется.
- **R-05** `✓` **Остановка IPC:** повторные `StopAsync` ожидают одну и ту же остановку,
  подключения и accept-loop закрываются с ограниченным ожиданием; таймауты логируются.
- **R-06** `✓` **Завершение Core:** shutdown-событие доставляется с ограниченным ожиданием;
  startup защищён `try/finally`, а модули и IPC останавливаются при завершении/отмене запуска.
- **R-07** `✓` **Освобождение IPC из DI:** `IpcServer` поддерживает синхронное и асинхронное
  освобождение, поэтому синхронное закрытие Generic Host корректно.
- **R-08** `✓` **SQLite busy timeout:** таймаут применяется при инициализации каждого соединения;
  интеграционные тесты проверяют конкурентную запись и завершение после освобождения блокировки.
- **R-09** `✓` `NotificationStore` и `ProfileStore` закрывают соединение при ошибке; при
  SQLITE_CORRUPT/NOTADB выполняется явная диагностика с указанием сохранённого файла, без
  автоматического затирания базы. Проверяется интеграционными тестами.
- **R-10** `✓` **Повреждённый журнал восстановления:** если основной файл повреждён, валидная
  `.bak` восстанавливается, а исходник сохраняется в `.corrupt-*` с предупреждением в логе.
  Если резервной копии нет или она тоже повреждена, модуль останавливается с явной ошибкой,
  исходный файл и резервная копия остаются на месте для ручного восстановления.
- **R-11** `✓` **Очередь истории уведомлений:** переполнение явно логируется и учитывается
  счётчиком отброшенных уведомлений; запросы к остановленному обработчику отклоняются сразу,
  фоновый сбой закрывает очередь и завершает ожидающие запросы ошибкой. После остановки при
  повторном старте создаётся новая очередь. Интеграционные тесты покрывают переполнение,
  порядок очистки, запрос после остановки и повторный старт.
- **R-12** `✓` **Гонка публикации Tray snapshot:** обновление подписи защищено синхронизированным
  tracker'ом с порядковым номером сканирования; запоздавший параллельный снимок больше не перезаписывает
  состояние более нового и одинаковая подпись не публикуется повторно. Проверяется интеграционными

## 3. Безопасность IPC — P1

Грозит локально: любой процесс в сессии пользователя может подключиться к каналу.

- **S-01** `✓` **ACL канала не задан:** `PipeSecurity`/`SetAccessControl` — ноль вхождений
  (`IpcServer.cs:77-82`), хотя `docs/Architecture/ipc.md:5` утверждает обратное. Имя канала —
  SHA256 от `domain\user` (`TrayXIpc.cs:13-15`), выводим по логину; аутентификации пира нет.
  Сложность **С**.
- **S-02** `~` **Версия протокола не проверяется:** у `IpcEnvelope` нет поля версии (`:7-17`),
  `ProtocolVersion` только кладётся в payload (`IpcRouter.cs:319,339`) — handshake отсутствует,
  вопреки `ipc.md:12,17`. Сложность **С**.
- **S-03** `✓` `sound.preview` принимает только абсолютные локальные WAV-пути; UNC/device-пути
  и mapped network drives отклоняются до проверки файла и вызова WinMM. Integration tests покрывают
  UNC/device paths и локальный системный диск.
- **S-04** `✓` `apps.launch` сверяет ID, путь и источник с каталогом приложений, созданным
  TrayX; произвольные клиентские пути не запускаются. Проверка файла выполняется непосредственно
  перед запуском ярлыка.
- **S-05** `~` **Деструктивные команды без подтверждения:** `tray.restart-explorer`
  (`IpcRouter.cs:209`) и `core.shutdown` (`:321`) доступны любому подключённому клиенту.
  Сложность **Н**.
- **S-06** `✓` Внутренние исключения журналируются на стороне TrayX; IPC-клиент получает
  безопасное общее сообщение без путей и внутренних деталей (ошибки обработчика команд локализованы).
- **S-07** `~` **Отказ в запуске через мьютекс:** `Local\TrayX.*` может быть заранее занят любым
  процессом сессии, и Core «вежливо» выходит (`TrayXIpc.cs:18`, `Program.cs:67-82`).
  Сложность **Н**.
- **S-08** `~` `IpcJson` ограничивает глубину 32 уровня; Named Pipe ограничивает входное
  сообщение 1 МиБ до разбора. Параметры, передаваемые COM, всё ещё требуют проверки диапазонов
  по каждому IPC-вызову.
